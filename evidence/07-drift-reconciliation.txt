  # selfHeal is off - but that is not yet enough to introduce drift safely.

  # This commit changed main, and the platform Application tracks main too.

  # A new revision is a change in *desired* state, which an automated sync

  # acts on whether or not selfHeal is set: selfHeal governs drift in the

  # live cluster, not new commits. So a sync is still pending, and when it

  # runs it applies every manifest in k8s/ - erasing any drift introduced

  # before it lands.

  # And there is a second, sharper trap underneath that one, which cost this

  # script three wrong runs before the controller log gave it up.

  # selfHeal: false does not mean 'never revert drift'. The controller skips

  # the automated sync only when it has ALREADY ATTEMPTED a sync at the

  # current revision - that is the 'Already attempted sync: comparing synced

  # revisions to [...]' line in its log. This commit touches gitops/apps/ and

  # not k8s/, so the manifests this Application reads are byte-identical to

  # the previous revision and no sync runs for it: the app reports Synced at

  # a revision it has never actually applied. Its last recorded operation is

  # for an older commit. So the next divergence, whatever causes it, is not

  # judged as drift at all - it is judged as an unsynced revision, and the

  # controller performs a FULL automated sync that erases the drift as a

  # side effect. In the log that is 'Initiated automated sync' with an empty

  # resource list, at the same second as the drift, which is easy to read as

  # selfHeal working. It is not: a self-heal names the resource it is

  # repairing and carries a SelfHealAttemptsCount, as PART 5 below shows.

  # 

  # The fix is to give the Application a sync operation at the current

  # revision, so a later divergence is judged on its own. It applies the same

  # manifests it already has, and changes nothing in the cluster.
