  # Four minutes, in phases, so each panel has something distinguishable:

  #   0:00-1:00  steady light traffic on / and /api/info

  #   1:00-2:00  burst: same routes, much higher rate

  #   2:00-3:00  slow requests (/api/work) - latency and in-flight rise

  #   3:00-3:30  errors: /api/boom (500) and a path that does not exist (404)

  #   3:30-4:00  CPU burn (/api/cpu) - the cAdvisor panel moves

  #   throughout  notes are appended, so the application-state metric climbs

STEP: What these numbers say about the application
---------------------------------------------------------------

  # Request rate follows the generator exactly: a low baseline, a burst an

  # order of magnitude higher, then a slow-request phase where the rate falls

  # while latency and concurrency rise - which is the signature of work

  # queueing rather than of traffic disappearing. Those two look identical on

  # a request-rate graph alone and completely different once in-flight and

  # the latency histogram are next to it.

  # 

  # The 5xx ratio is non-zero only during the error phase, and the 404s are

  # separated from the 500s by the status label, so 'clients asking for the

  # wrong thing' never gets confused with 'the server is failing'.

  # 

  # Container CPU rises only in the last phase, when /api/cpu is spinning.

  # During the slow-request phase CPU stays flat while latency is at its

  # worst - the workload is waiting, not computing. That distinction is the

  # reason both an application metric and an infrastructure metric are on the

  # same dashboard.

  # 

  # cse644_api_notes_stored only ever climbs, including across the Pod

  # replacements in the earlier demonstrations. It is application state on a

  # PersistentVolume, and a drop to zero would mean the volume was lost.
